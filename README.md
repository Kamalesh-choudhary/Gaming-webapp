# READ // Opponent-Modeling Game

A full-stack game (Rock-Paper-Scissors + Tic-Tac-Toe) where the AI opponent
builds a live statistical model of *you* — your move frequencies and your
short-term sequential habits — and uses it to play against you, not just the
rules.

Flask REST API backend, vanilla HTML/CSS/JS frontend (no build step, no
page reloads), server-side per-session state.

## Quick start

```bash
pip install -r requirements.txt
python app.py
```

Open `http://127.0.0.1:5000` in your browser.

## How the opponent modeling works

The core of the project is `ai_engine.py`'s `PatternAnalyzer` class, a
reusable statistical model that blends two classic prediction techniques:

**1. Frequency analysis** — the simplest baseline: what has the player
played the most, overall? On its own this is easy to counter (a player who
notices the AI is guessing their most-common move will just diversify), but
it's a good fallback when there isn't much history yet.

**2. Markov chain / n-gram analysis** — humans are bad at behaving randomly.
Most players fall into short habits: "switch after a loss," "repeat after a
win," "cycle rock → paper → scissors." The analyzer keeps a table of
`P(next move | last N moves)` (N=2 by default for RPS, N=1 for Tic-Tac-Toe)
and updates it after every move. Once it has seen the player's current
2-move context before, it leans on that sequential pattern instead of the
flatter overall frequency.

**Blending & decay** — the two predictions are combined, with the Markov
model's weight increasing as more history accumulates for the *current*
context (capped at 75%, so frequency data always has some say). Every
recorded move also slightly decays older observations (`decay=0.98`), so
the model keeps adapting if a player changes strategy mid-game instead of
being permanently anchored to their first ten moves.

```
predicted_move, confidence, full_distribution = analyzer.predict()
```

### How each game uses the prediction

- **Rock-Paper-Scissors (`RPSAI`)** — before your move for the round is
  known, the AI predicts it and plays the counter-move (e.g. predicts
  "rock" → plays "paper"). A small exploration rate (12%) makes it
  occasionally ignore its own prediction and play randomly, so it can't be
  trivially reverse-engineered by a player who is smart about their fake
  "tells."

- **Tic-Tac-Toe (`TicTacToeAI`)** — perfect-information games like
  Tic-Tac-Toe are a solved problem, so this AI plays optimal minimax with
  alpha-beta pruning and can never lose, no matter what pattern modeling
  says. The `PatternAnalyzer` is still put to use, though: whenever
  minimax finds multiple equally-good moves, the AI breaks the tie by
  favoring the cell it predicts the player is statistically most likely to
  want next. It's honest, not oversold — the model can't out-strategize
  perfect play, but it does make the AI's behavior feel personalized
  instead of purely mechanical.

## API

All endpoints return JSON. `session_id` is generated by the server on
`/new-game` and must be sent back on later requests, either as the
`X-Session-Id` header or in the JSON body.

| Method | Path        | Body / Query                              | Description |
|--------|-------------|--------------------------------------------|--------------|
| POST   | `/new-game` | `{ "mode": "rps"\|"tictactoe", "session_id"?: str }` | Starts a game. Reusing an existing `session_id` for the same mode resets the board but **keeps** score and the trained AI model. |
| POST   | `/move`     | `{ "session_id": str, "move": ... }`      | RPS: `move` is `"rock"\|"paper"\|"scissors"`. Tic-Tac-Toe: `move` is a cell index `0-8`. Returns the AI's move, the result, updated score, and the AI's pre-move prediction. |
| GET    | `/stats`    | `?session_id=...`                          | Returns score, full round history, and the AI's current model stats (move frequencies, total moves seen). |

## Session handling

Each session's state (score, move history, board, and the AI model
instance itself) lives in an in-memory Python dict on the server, keyed by
`session_id` — not in a browser cookie. This means:

- Two players in two browser tabs each get their own isolated AI; one
  player's habits never bleed into another's model.
- The client only ever holds an opaque ID (persisted in `localStorage` so a
  page refresh resumes your game), never any game state itself.

**Production note:** an in-memory dict is intentionally simple for a
portfolio/demo project. It won't survive a process restart and won't scale
across multiple worker processes/machines. Swapping in Redis (or any
keyed store) behind the same `SESSIONS`-shaped interface would make this
horizontally scalable without touching the game logic.

## Design notes

The UI leans into the subject matter — a live "opponent model" reading you
— rather than decorating a generic game skin: a persistent confidence
meter shows the AI's read on your next move *before* it commits to its
own, and a frequency panel shows exactly what the model has learned about
you so far, updating after every move.
